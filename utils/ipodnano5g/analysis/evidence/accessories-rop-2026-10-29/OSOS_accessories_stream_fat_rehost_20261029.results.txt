# Original stream-to-FAT wrap rehost (29.10.2026)

`qemu-arm -cpu arm1176` exits with code 0 and prints `PASS`. The harness invokes the original `FUN_08039048`, so the four-byte length field is read from the wrapped candidate, then the same helper issues the `0xfffffff0` payload request with `max_length=0x100`.

The test state is primed manually: the 704-byte candidate is the outer stream buffer, its read position is `0x1c`, and the inner file cursor is at logical EOF `0x2c0`. This corresponds to the parser having consumed its preceding tokens and the stream having filled its buffer; the harness does not execute the VFS open or the initial prefetch.

The payload read reports `0x1fa0` bytes: 672 bytes from the candidate after offset `0x20`, plus 7424 bytes reported by the original wrapper/provider path after logical EOF. The FAT core also copies the final partial chunk through offset `0x1fe0`; assertions verify candidate bytes at the start, `0x41` cache-stub bytes through `0x1fdf`, and the untouched sentinel at `0x1fe0`. The saved-LR word at `0x138` is exactly the candidate gadget `0x08007107`.

Original runtime functions listed in the `.run.log` execute in the trace. Cache lookup, sector-to-buffer mapping, FAT-chain/EOC, ATA read, file open, and the external memcpy veneer are stubs. The outer stream state and candidate bytes are synthetic, and the sampled buffer is a rehost destination, not the actual `FUN_0802c3c4` stack frame. This demonstrates read-path reachability and byte placement under the documented state; it does not establish a device run, real cache contents, parser return control, ROP completion, loader execution, or persistence.
